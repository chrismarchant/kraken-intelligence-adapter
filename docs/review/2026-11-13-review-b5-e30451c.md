## The decision-request change

A request that came to nothing is now removed when the same decision is asked for again. The reviewer walked through what that does to the approval path:

| Question | Result |
|---|---|
| The editor looks at a request, it expires, the agent asks again, and the editor confirms the first | Refused as an unknown request; nothing recorded |
| The editor confirms the new request with the first one's digest, or its code | Refused: the digest binds the request's id, so it cannot be carried over, even when the content is identical |
| Is a request that is still waiting ever removed? | No. Two live requests for the same decision both stayed. A request that expires at the very moment of the new one is kept, which matches the rule used at confirmation |
| Is a confirmed request ever removed? | No. Nothing in verification, in the reading of approvals, in assembly or in the operator tool reads the requests at all; with every request deleted, the decision log and assembly still check out |
| Guesses at a confirmation code | Before: at most 5,000 over a campaign's life. Now: no total. Practical effect none: a code is 128 random bits, no MCP tool takes one, and a correct code records nothing without the operator's key |
| Can a campaign be locked out of decisions by asking again? | No |

Byte-identical between `1f159a2` and `e30451c`: the operator tool, signing, the ledger, every contract, assembly and the spend account. In the workflow service only `requestDecision` changed.
